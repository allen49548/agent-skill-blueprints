# Agent Skill Blueprints

Four **self-contained, runnable** capability skills. Clone the repo, run one command, answer a short wizard, and you are live. No dependencies, no credentials, no per-user code changes, no vendor SDKs.

Python 3.9+ standard library only. Current version: **0.2.0** ([changelog](CHANGELOG.md)).

## Quick start

```bash
git clone git@github.com:allen49548/agent-skill-blueprints.git
cd agent-skill-blueprints/skills/document-intake-ledger

python3 run.py demo      # zero config, bundled sample data, full pipeline
python3 run.py setup     # 9-step interactive wizard -> config.json
python3 run.py doctor    # validate config, adapters, permissions
python3 run.py run       # dry-run by default; --no-dry-run for real writes
```

`demo` is the proof that it works: it reads bundled records, deduplicates them, writes XLSX / CSV / JSON, renders all four notification templates and leaves a run log under `demo-out/`. It needs no config file and no network access.

`setup --yes` accepts the recommended preset without prompting. `python3 run.py install --apply` copies the skill into `~/.workbuddy/skills/<slug>/` so an agent can invoke it directly. Substitute any of the four package directory names above; they all work the same way.

## Read this first: what actually runs

The shared runtime is real, tested code. The four *capability-specific* mechanisms are **target designs**, not implementations. `profile.json` changes defaults, not algorithms. Check [docs/capability-matrix.md](docs/capability-matrix.md) before relying on any invariant.

| Area | Status |
| --- | --- |
| demo / setup / doctor / run / info / install / build | Implemented and tested |
| Local folder, JSON, webhook inputs; CSV, JSON, XLSX outputs | Implemented and tested |
| Four notification templates; business-key dedup ledger | Implemented and tested |
| Dry-run, backup, byte-identical verification | Implemented and tested |
| Feishu / WeCom group listing and messaging | Contract only; a project-supplied adapter is required |
| Installing a scheduled job | Config only; nothing schedules the run |
| Independent recomputation and approval gate, OCR, semantic normalization, timezone ranking | Target design, **not implemented** |

This is a working skeleton you extend, not four finished products. Saying so plainly is deliberate.

## Why there is no learning cost

| Concern | How it is handled |
| --- | --- |
| Different users, different data | Every difference lives in `config.json`, generated by the wizard. The code is identical for everyone. |
| Different platforms | Input, output and notification are adapters. Built-in ones (local folder, CSV, JSON, XLSX, stdout) work with zero credentials; real platforms are registered, never hardcoded. |
| First-run fear | `demo` runs the whole pipeline on sample data. `run` is dry-run by default. `doctor` explains any problem. |
| Installing as a skill | `install --apply` copies the package into the local skills directory. Nothing to wire by hand. |
| Want to change your mind | `setup` can be re-run; choices are never inferred from an earlier session. |

## The four skills

| Package | Capability | Reach for it when | Do NOT reach for it when |
| --- | --- | --- | --- |
| [scheduled-digest-publisher](skills/scheduled-digest-publisher/) | Aggregate sources into a period-keyed digest, highlight one focus entity, normalize timezones, deliver once | Recurring briefing, status digest, release-notes roundup, event schedule | Real-time push or a one-off report with no delivery step |
| [verified-batch-calculation](skills/verified-batch-calculation/) | Compute per-entity results, verify independently, deliver behind an approval gate | High-stakes results, per-entity rules, a wrong number must never be sent | Reversible low-stakes single-pass calculations |
| [message-to-workbook-sync](skills/message-to-workbook-sync/) | Parse semi-structured messages and write normalized values into existing workbooks at cell level | The workbook layout is fixed and must not be structurally changed | You own the form and can write structured records directly |
| [document-intake-ledger](skills/document-intake-ledger/) | Extract records from documents, deduplicate through a ledger, append rows, drive a status machine | The same document can be submitted twice and double-counting is the main risk | A trusted API already guarantees exactly-once delivery |

Each package is standalone: copy its directory anywhere and it still runs.

## Commands

| Command | What it does | External effects |
| --- | --- | --- |
| `demo` | Full pipeline on bundled sample data | Local artifacts only |
| `setup` | Nine-step wizard; writes `config.json` | None |
| `doctor` | Validate config, `*_ref` pointers, adapters, timezone, dry-run state | None |
| `run` | Real pipeline, dry-run by default | Change log only |
| `run --no-dry-run` | Real pipeline with writes and sends allowed | Configured adapters only |
| `info` | Show profile and config status | None |
| `install --apply` | Copy this skill into the local skills directory | Local copy |

## The wizard

Nine steps: preset or custom, platform, list-all-groups multi-select, message source types, output target, notification templates, schedule, full review, trial run. New report creation is the one action that needs explicit authorization. Every choice is echoed before anything is written.

Full contract: [docs/onboarding-contract.md](docs/onboarding-contract.md). Applicability differs per package; steps that do not apply are skipped with an explanation.

## Development

```bash
python3 -m unittest discover -s tests -v   # 22 tests, standard library only
python3 tools/check_repo.py                # encoding, privacy, JSON, structure gate
python3 build.py && python3 build.py --check   # standalone packages in dist/
```

CI runs the tests, all four demos, the build and the hygiene gate on Python 3.9-3.13 for every push and pull request. See [CONTRIBUTING.md](CONTRIBUTING.md) before changing the runtime: there is exactly one `skillkit/engine.py`, and the four `run.py` files are shims. To ship a single skill elsewhere, run `build.py` and copy `dist/<slug>/`.

## Design principles

1. **Name the mechanism, not the domain.** No business roles, brands or project names in identifiers or concepts.
2. **Configuration over constants.** Identifiers, paths, thresholds and schedules are config fields, never code.
3. **Invariants are first-class.** Each package states the rules that must never break, separately from flexible procedure.
4. **Idempotency by default.** Re-running is safe; duplicates are detected by business key, never by equal value.
5. **Human gates on irreversible actions.** Approval, delivery and real writes are explicit; dry-run is the default.
6. **Never mutate source material.** Writes into existing files are surgical, backed up and verified.
7. **Failures are visible.** Degradation is allowed; silence is not. Every skip and failure lands in the run log.
8. **English only.** Names, concepts, docs, examples and comments use English.

Canonical vocabulary: `entity`, `channel`, `workbook`, `approver`, `recipient`, `source`, `run`, `ledger`. See [docs/vocabulary.md](docs/vocabulary.md).

## What is deliberately absent

- Real platform API calls. `feishu` and `wecom` are config option values; the network call is an adapter slot.
- Automatic scheduling. `setup` records a cron expression and timezone, but no scheduler is installed.
- The four capability-specific mechanisms. See the matrix above and `docs/capability-matrix.md`.
- Real names, account/chat identifiers, absolute machine paths, amounts, screenshots and database state.
- Domain-specific reward, penalty, ranking or wording policies.
- Third-party marketplace skills and author-side maintenance tooling.

## Release checklist

Before any public push, run `python3 tools/check_repo.py` and `python3 -m unittest discover -s tests`. Both are also enforced in CI. If implementation status changed, update `docs/capability-matrix.md` and `CHANGELOG.md` in the same pull request. The longer publishing and privacy pre-flight procedure is in [PUBLISHING.md](PUBLISHING.md).
